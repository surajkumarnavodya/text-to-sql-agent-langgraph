## 1. The natural-language → SQL → result flow, traced from the real graph wiring

`agent/graph.py::build_graph()` (verified via `add_node`/`add_edge` calls,
not assumed) wires exactly these 12 nodes, entry point `sanitize_input`:

```
sanitize_input -> classify_followup -> retrieve_schema -> retrieve_golden_examples
  -> retrieve_business_context -> plan_query -> generate_sql -> review_sql
  -> validate_sql -> estimate_cost -> execute_sql -> generate_insight -> END
```

Conditional edges (not shown above) route a review/validation/cost/execution
failure back to `generate_sql`, or a "missing reference" execution error
back to `retrieve_schema`, bounded by `state["max_retries"]`
(`agent/complexity.py::compute_max_retries`, not a flat constant) — see
`docs/ARCHITECTURE.md` §2 for the full per-category routing table, which
was spot-checked against `agent/nodes.py`'s actual routing functions and
found accurate.

`AgentState` (`agent/state.py`, a `TypedDict`) carries `selected_database`
and `selected_model` — both resolved exactly once, read-only downstream,
verified as the pattern every retry path actually reuses rather than
re-selecting.

When `ENABLE_MULTI_SOURCE_ROUTER=true`, `agent/orchestrator/graph.py`
wraps this entire graph as one opaque `sql_subgraph` node alongside
`document_rag`/`policy_rag`/`web_search`/`generation`/`media_search`/
`attachments` — confirmed the flag-off path (`agent.orchestrator.graph
.run_orchestrated`) still calls `agent.graph.run_agent` directly with the
orchestrator graph never constructed, by reading the function body, not
by trusting the docs.

## 3. Duplication scan (rule 3) — clean

## 4. Truth-provenance gap analysis (rules 9 & 10)

**No `DATABASE_FACT`/`AI_INFERENCE`/`CONFIRMED_BUSINESS_TRUTH` vocabulary
exists anywhere in this codebase today** (repo-wide grep, project source
only, zero hits). This is genuinely new work, not a rename of something
existing. But three real mechanisms already enforce a version of this
distinction in practice and are the concrete extension points:

1. **`agent/insight.py`'s grounding gate** is the strongest existing
   analog to "never silently convert AI_INFERENCE into
   CONFIRMED_BUSINESS_TRUTH." `ResultSummary` (a `ColumnStat`/aggregate
   summary) is computed deterministically in Python from the *actual*
   query result — this is `DATABASE_FACT`. `generate_insight_from_llm`'s
   output is `AI_INFERENCE` — an LLM narrative sentence. `is_insight_grounded()`
   rejects any numeric/percent claim in that narrative that isn't
   traceable to `ResultSummary.allowed_values()`/`allowed_percents()`,
   i.e. it structurally prevents an ungrounded inference from reaching
   the user framed as fact. This pattern (compute-then-constrain, never
   let the LLM assert an unverifiable number) is exactly what a future
   prompt should generalize into an explicit typed contract, rather than
   reinventing grounding logic per feature.
2. **Golden examples** (`embeddings/golden_examples.py`) are the closest
   existing analog to `CONFIRMED_BUSINESS_TRUTH` for SQL specifically — a
   human explicitly promotes an AI-drafted-then-corrected query into a
   trusted, reusable example via an explicit UI action (thumbs-up after
   "Confirm and Run"), never automatically. The promotion step already
   exists; it's just not labeled with this vocabulary or generalized
   beyond SQL.
3. **`config/table_descriptions.yaml`/`config/sensitive_columns.yaml`**
   are hand-reviewed, human-authored business semantics overlaid onto
   live schema DDL at retrieval time — another real (if narrow) example
   of "a human, not the LLM, is the source of confirmed business
   meaning."

**Recommendation for a later prompt**: introduce one small, shared typed
module (e.g. `agent/provenance.py`) defining the three states as an
explicit enum/tagged union, and retrofit `ResultSummary`/insight output,
golden examples, and any new recommendation output to carry this tag —
rather than each new feature inventing its own ad hoc "is this confirmed"
flag.

## 5. SQL Server assumptions and hard-coded business semantics

- **`rag/store.py`** (document/policy RAG) requires SQL Server 2025+ or
  Azure SQL specifically, for the native `VECTOR` column type — a real,
  disclosed constraint separate from the four `DB_TYPE`s
  (`postgresql`/`mysql`/`mssql`/`oracle`) the core SQL pipeline supports.
- **`moderation/store.py`** also requires a dedicated SQL Server
  connection, for the same reason.
- **`config/table_descriptions.yaml`/`config/sensitive_columns.yaml`**
  are keyed by bare table name, not `(database, table)` — a disclosed,
  narrow limitation if two configured databases share a table name.
- **`config/column_labels.py`**'s `ABBREVIATION_EXPANSIONS` dict
  (`"Cust"` -> `"Customer"`, `"Qty"` -> `"Quantity"`, etc.) is hand-tuned
  for the AdventureWorksDW2025 sample schema's own naming conventions —
  a real, narrow, disclosed piece of hard-coded business semantics that
  a genuinely generic analytics platform would need to make
  schema-configurable rather than a single static dict.
- **`data/knowledge/`**'s sample business-context content (glossary,
  metrics) is explicitly labeled illustrative demo content, not reviewed
  production documentation (`CLAUDE.md`'s own disclosure, confirmed
  still true by inspection).

## 6. Security boundaries and blocking-work notes

- **Security boundaries are layered, not single-point**: SQL validator
  (AST allowlist) -> read-only DB role (operator responsibility,
  `db.connection.check_write_privileges` startup-checks it) -> RBAC
  (`agent/authz.py`, enforced *before* the orchestrator router picks a
  subgraph, not just at the API edge) -> tenant/ownership scoping
  (currently real only for conversation sharing, see §2/§6 tenant row).
- **Blocking work, not yet async**: every LLM call (`agent/llm_client.py`)
  and every SQL execution (`db/execution.py`) is a synchronous call
  occupying a request thread — bounded now by `Settings
  .max_concurrent_ask_requests`'s `ThreadPoolExecutor` (real admission
  control, added in the Scale-out program), but there is still no true
  async request handling or cross-thread cancellation
  (`docs/SCALE_OUT_PROMPT.md`'s own disclosed Phase 1 scope). Any new
  analytics/recommendation feature that adds its own LLM/DB calls
  inherits this same constraint and should be sized against the existing
  `max_concurrent_ask_requests`-vs-DB-pool sizing warning
  (`api/main.py::_warn_on_ask_concurrency_pool_mismatch`), not a fresh
  capacity assumption.
- **Frontend/backend coupling**: the React dashboard is served by the
  same FastAPI process (`api/main.py`'s `StaticFiles` mount) at the same
  origin — no `/api` prefix, no CORS needed for the common deployment
  shape. A new analytics/recommendation UI surface should follow this
  same single-origin convention rather than introducing a second
  frontend origin/build.
